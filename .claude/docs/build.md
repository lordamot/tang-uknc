# Building and flashing

Two binaries, two toolchains.  What ships prebuilt is:

```
bin/tang.fs      7261987 bytes, Jan 2025   the FPGA bitstream
bin/bl616.bin     430512 bytes, Aug 2026   the MCU firmware
```

The two are **not at the same point**.  `bin/bl616.bin` is rebuilt from
`mnano/` whenever the firmware changes, because this host can build it.
`bin/tang.fs` cannot be rebuilt here at all, so it stays at whatever the
last Gowin run produced - January 2025 - and does not contain any RTL
change made since.  `howto.md` says so where a user will see it.

A user who only wants to run the machine flashes those two and needs no
toolchain at all.  That is the point of committing them.

> `bin/tang.fs` and `tang/impl/pnr/test003.fs` are the same size and the
> same date but **not the same file** (different md5).  Which of the two is
> the one running on a board has not been established.  Treat `bin/` as the
> shipped one until someone says otherwise.

**Both halves build on this host.**  Everything they need lives under
`tools/`, fetched by `make toolchain` - about 8 GB including Gowin -
nothing is installed on the host and `tools/` is in `.gitignore`.

```
make toolchain   fetch the toolchain into tools/  (~8 GB, once)
make bitstream   build the FPGA bitstream -> bin/tang.fs
make lint        Verilator over the whole design - the fast check
make sim         run the machine, boot and all
make wave        the same, dumping a VCD, then open it (WAVE_MS=2)
make frames      the same, writing video frames as .ppm (needs 45 ms+)
make fw          build the BL616 firmware -> build/fw/bl616.bin
make mif         ROM images -> build/mif/*.hex for the sim models
make flash-fpga  openFPGALoader the shipped bitstream to SRAM
make flash-mcu   flash the firmware over UART (COMX=/dev/ttyACM0)
```

`tools/env.sh` puts the same toolchain on `PATH` for running any of it by
hand; the Makefile does that for itself.

Three sizes worth knowing before you type one of these:

- **`make wave` builds a second simulator binary.**  Verilator's
  `--binary` ignores `$dumpfile`/`$dumpvars` unless the model was
  generated with `--trace`, and tracing costs enough that `make sim`
  should not carry it - so there are two binaries, `build/sim/obj` and
  `build/sim/objw`.  The VCD runs about **25 MB per simulated
  millisecond** over 2390 signals, hence `WAVE_MS ?= 2`; raise it
  deliberately.
- **`make frames` needs `RUN_MS` of 45 or more.**  A frame is written on
  the vsync that ends it, and the first one ends at 39 ms.  They are
  binary P6, 1280x600, 2.3 MB each; `PPM_MAX ?= 4` caps how many.  Since
  August 2026 those frames are **decoded back out of the TMDS stream**
  rather than tapped off the RGB signals, so a frame that comes out right
  is a statement about `src/hdmi/` and not just about `sdram2.v`.
- **`make sim` runs at about 10 ms of simulated time per wall second**, so
  the default 300 ms is half a minute and a second of machine time is two
  and a half minutes.

### What the simulation covers, and what it stubs

`tools/srcs.py` reads the file list out of the `.gprj` and splits it in
two: everything under an `ip/` directory is vendor IP and is replaced
wholesale by `sim/stubs/gowin_ip_sim.v`, and so is anything named in that
script's `STUBBED` list.  There is one entry in it,
`src/hdmi/hdmi_serdes.v`, and the reason is the same as for the IP - it is
nothing but `rPLL`, `OSER10` and `ELVDS_OBUF`, which Verilator has no
models for.

Everything above it is simulated for real, and the testbench decodes what
comes out: `sim/tb/tb_top.v` follows the preambles and guard bands the way
a sink does, rebuilds the picture from the video periods and pulls the
data island packets apart, checking their ECC.  The end-of-run line reads

```
[tb] hdmi: 177876 packets, 0 ecc errors  (acr 14823, avi 14823, ai 14823, audio 69482, null 63925)
[tb] hdmi audio: 69482 samples, 0 with sound, 0 with L != R, overflow=0
```

and `+HDMIDBG` prints every packet.  "0 with sound" is normal on a run
where nothing plays; `+AUDIOTEST` forces two constants onto the AY mix and
turns it into a real answer.

## The FPGA half

Toolchain: **Gowin EDA Education edition**, V1.9.11.03, fetched into
`tools/gowin/` by `make toolchain`.  It is a free download and needs no
licence file for the GW2AR-18C.  `make bitstream` drives its headless
shell:

```
make bitstream          # ~1 minute; writes tang/impl/pnr/test003.fs and bin/tang.fs
```

The Tcl it runs is generated by `tools/gowin_tcl.py` from
`tang/test003.gprj` plus the IDE's own
`tang/impl/test003_process_config.json`, so the command-line build and an
IDE build read the same file list and the same options and cannot drift.
The IDE route still works if you have it:

```
open tang/test003.gprj in the Gowin IDE
Synthesize  ->  Place & Route  ->  tang/impl/pnr/test003.fs
```

Three things about `gw_sh` that cost an hour to find, all handled for you
but worth knowing before you edit any of it:

- **Its bundled libraries fight a current Linux.**  It ships an old
  libstdc++, an old freetype, and - in the same install - a 2019 Qt5Core
  next to a 2025 Qt.  `tools/fetch.sh` moves the stale duplicates into
  `_shadowed/`, and the Makefile wraps `gw_sh` in `LD_LIBRARY_PATH`,
  `QT_PLUGIN_PATH` and `QT_QPA_PLATFORM=offscreen`.  Without that it fails
  with `GLIBCXX_3.4.14 not found`, then `FT_Done_MM_Var`, then "Cannot mix
  incompatible Qt library (5.15.18) with this library (5.15.14)".
- **Option names differ from the IDE's.**  `ram_rw_check` is
  `-rw_check_on_ram` here.
- **`-use_sspi_as_gpio 1` is not optional.**  HP_BCK, HP_WS and HP_DIN are
  on pins 56/55/54, which are the SSPI pins; without freeing them
  placement fails with PR2017.  The IDE keeps that setting in
  `test003_process_config.json` (`SSPI = True`) and `gowin_tcl.py` reads
  it from there.

Options the project carries (from `impl/gwsynthesis/test003.prj`): top
module `top`, `global_freq 100.000`, `verilog_language sysv-2017`,
`ram_rw_check 0`.  The `sysv-2017` setting is load-bearing - `ay/ym2149.sv`
is SystemVerilog.

Note that `impl/gwsynthesis/test003.prj` still holds the author's absolute
paths (`/workspace/verilog/tang20/2024/uknc/test003ho/...`).  The IDE
rewrites it on the next synthesis; do not try to keep it in sync by hand.

Flashing: the Gowin Programmer, or `make flash-fpga` (openFPGALoader to
SRAM, gone at power-off) / `make flash-fpga-flash` (to the on-board flash,
kept).

### Timing constraints

`tang/src/test003.sdc` has been in the project since August 2026 and is
run on every build.  As it stands: 13809 paths analysed, **0 setup
violations**, 559 hold ones - and those 559 are an artefact of how
`clk_25` and `clk_3_12` have to be declared, not a finding.  The file's
own header has the numbers and the reasoning; read it before changing
anything, and see defect 3 in `.claude/docs/progress.md`.

### What lint and simulation do cover

`make lint` runs Verilator over exactly the file list in
`tang/test003.gprj` - `tools/srcs.py` reads the project XML, so the two can
never drift - with `sim/stubs/gowin_ip_sim.v` standing in for the vendor IP
(three of those files are encrypted, and the rest need the Gowin primitive
library).  It reports **zero errors** on the tree as it stands, so any
error is yours.  It reports plenty of warnings, which are the author's.

`make sim` builds the whole machine into a Verilator binary against a
1024-word-page SDRAM model and a stand-in BL616 that speaks the real SPI
protocol.  It boots.  See `.claude/docs/progress.md` for what it showed.

There is **no `synth` target**.  Yosys is in the toolchain and was worth a
try as a second front end, but it segfaults on these sources at
`read_verilog`; it could never have produced a bitstream anyway, since
`dvi_tx`, `fifo_audio` and `uartfifo` are encrypted.  (`dvi_tx` is no
longer instantiated - `src/hdmi/` replaced it - but it is still in the
project as the fallback.)

None of this replaces a board.  Lint and simulation catch missing modules,
port and width mismatches, inferred latches and gross protocol errors -
the things that otherwise cost a 40-minute round trip through the IDE.
They say nothing about timing (there are no constraints at all - defect 3
in `progress.md`) and nothing about the real SDRAM, the real HDMI PHY or
the real card.  Never say a change "works" on the strength of a simulation.

## The MCU half

Toolchain: the **Bouffalo SDK** plus a **T-Head RISC-V** GCC, both fetched
into `tools/` by `make toolchain`.  `make fw` builds them into
`build/fw/bl616.bin`.

Three things had to be settled to make that work, and they are worth
knowing because they will look like breakage otherwise:

- **The SDK is pinned to `master_legacy`.**  Master has moved on from the
  2024 CherryUSB API this firmware was written against - `struct usbh_hid`
  lost `report_desc`, `usbh_initialize()` grew arguments - and
  `mnano/usb_host.c` will not compile against it.  `master_legacy` still
  carries the old API.  Neither branch reaches back to 2024 exactly, so
  this is the closest vintage that can still be fetched.
- **`cmake/bflb_flash.cmake` is patched at fetch time.**  It picks the
  suffix of its host tools from `CMAKE_SYSTEM_NAME`, which for a
  bare-metal cross build is always `Generic`, so the stock SDK reaches for
  `bflb_fw_post_proc.exe` on every host and dies with "Exec format error"
  right after linking.  The patch reads `CMAKE_HOST_SYSTEM_NAME` instead.
- **Two `-D`s go in through `BOARD`.**  `-DM0S_DOCK=1` picks the SPI
  pinout in `mnano/spi.c` that matches this board's wiring (GPIO
  12/13/10/11/14 - see `README.md`; the file is upstream's unchanged, and
  the FPGA side is what moved to meet it), and `CONFIG_BT_STACK_CLI=0`
  drops a
  BLE debug shell that will not build against this SDK and that nothing in
  this firmware uses.

The binary that comes out is what `bin/bl616.bin` now is - `make fw`
copies it to `build/fw/bl616.bin` and it is copied on to `bin/` whenever
`mnano/` changes, because flashing straight from `bin/` without a
toolchain is what that directory is for.  It is around 430 KB against the
399808 bytes of the August 2024 binary it replaced, and is not
byte-comparable with it: that one was built against whatever the SDK was
then.  The old one is in git history.

`mnano/run_make` is the author's build line with his own paths in it.  It
is not a script to run as-is; `make fw` is the same thing with the paths
under `tools/`.

`CMakeLists.txt` and `proj.conf` are the SDK's build description;
`flash_prog_cfg.ini` and `misterynano_fw_bl616_cfg.ini` are the flasher's.

## Flashing the FPGA, and two things that will waste an evening

```sh
make flash-fpga            # SRAM, volatile - gone on the next power cycle
make flash-fpga-flash      # the SPI flash, survives
```

**`-f -r` writes the flash and does not reliably reconfigure the FPGA.**
The `-r` is in the Makefile and openFPGALoader reports success, but the
chip goes on running whatever configuration it already had.  So a write is
two steps: flash it, then **power-cycle the board** - and a run tested
without that second step is testing the previous bitstream.  This cost a
full test run in Aug 2026 before it was noticed.

**Opening the serial port poisons the next flash.**  Once anything has
opened `/dev/ttyUSB*`, openFPGALoader fails with

```
unable to open ftdi device: -6 (ftdi_usb_reset failed)
```

because the FT2232 is emulated by the on-board BL616 and will not accept
the USB reset that libftdi does when it opens a device.  `--skip-reset`
does not help: that flag is about the FPGA, and the reset happens inside
the device open, before it is consulted.  The only fix is to **replug the
USB-C cable**, which re-enumerates the device.  So the working order is
replug, flash, power-cycle, then read - and RTL changes are worth batching,
because each one costs that cycle.

Do **not** try to force it with a `USBDEVFS_RESET` ioctl on
`/dev/bus/usb/*`.  That does not recover the device; it drops it off the
bus entirely and needs a replug anyway.

### Reading the board

`tools/dbgmon.py` reads the diagnostic monitor - see
`.claude/docs/fpga.md`.  **The monitor is out of the build as of 31 Aug
2026**, so there is nothing on the line until it is instantiated again;
what follows is how to read it when there is.  It finds the port through
`/dev/serial/by-id/*if01*` rather than a `ttyUSBn` name, because that
number changes on every re-enumeration.

```sh
tools/dbgmon.py            # changed lines only
tools/dbgmon.py --all      # every line, ten a second
tools/dbgmon.py --raw      # undecoded, for when the word list moves
tools/dbgmon.py -t 300 > run.log
```

The user needs `plugdev` for the FTDI; that is a udev rule, not `dialout`,
and it is the same rule openFPGALoader relies on.

## Flashing the BL616

```sh
make flash-mcu COMX=/dev/ttyACM0                          # bin/bl616.bin
make flash-mcu COMX=/dev/ttyACM0 FW_BIN=build/fw/bl616.bin  # what make fw built
```

`FW_BIN` defaults to the shipped `bin/bl616.bin`; `BAUDRATE` defaults to
2000000, which is what the SDK uses.  The target refuses early - with a
sentence saying which - if the SDK is not fetched, if the firmware file is
not there, or if the port is not writable.

### Boot mode

The BL616 flashes over the **bootloader in its own ROM**, not over a
debugger, so the chip has to be started into it: **hold BOOT, tap RESET,
release BOOT.**  It then enumerates as a USB CDC port - `/dev/ttyACM0` on
a stock Linux, and `/dev/m0s_debugger` as well if the Bouffalo dock's udev
rule is installed.  The port only exists while the chip is sitting in the
bootloader; after a flash it resets into the firmware and the port comes
back as whatever the firmware presents.  `COMX` is that port, and the
Makefile cannot guess it, which is why it is the one thing you pass.

If the flasher prints `BFLB IMG LOAD HANDSHAKE FAIL` followed by a block
of Chinese, that is the tool's own list of things to check and it means
the same thing every time: it opened the port but nothing in the
bootloader answered.  The board is not in boot mode, or that is the wrong
port.

### Permissions

`/dev/ttyACM0` is `root:dialout`, so flashing needs membership of
`dialout`:

```sh
sudo usermod -aG dialout "$USER"
```

**A group added this way does not reach a process that is already
running.**  The credentials are fixed at login, so the shell you typed
that in, its parent terminal, and any long-running tool that spawns
shells from it all still have the old set - `id` will show `dialout`
missing while `getent group dialout` already lists you.  Log out and back
in - or don't, and run the one command under `sg`, which is setuid and
reads `/etc/group` rather than the caller's credentials:

```sh
sg dialout -c 'make flash-mcu COMX=/dev/ttyACM0'
```

That needs no password and no relogin, only that `/etc/group` already
lists you.  `newgrp dialout` is the same thing for an interactive shell.

The FPGA half does not need any of this: `openFPGALoader` talks to the
Tang's FTDI over USB, which is `plugdev`.

### No PATH, no install

The flasher is `BLFlashCommand-ubuntu`, a self-contained PyInstaller
bundle that comes down with the SDK:

```
tools/bouffalo_sdk/tools/bflb_tools/bouffalo_flash_cube/BLFlashCommand-ubuntu
```

It needs **nothing on `PATH`, no Python, and nothing installed on the
host** - an absolute path to the binary is the whole invocation.  Neither
`tools/env.sh` nor the RISC-V toolchain has anything to do with flashing;
they are for *building*.  There is one binary per host - `-ubuntu` is
x86-64 Linux, `-arm` is aarch64, and `project.build` picks between them by
`arch`.  Run it by hand as:

```sh
tools/bouffalo_sdk/tools/bflb_tools/bouffalo_flash_cube/BLFlashCommand-ubuntu \
  --interface=uart --baudrate=2000000 --port=/dev/ttyACM0 \
  --chipname=bl616 --config=build/flash/bl616.ini
```

`--config` is an ini naming the image and the address.  `make flash-mcu`
generates `build/flash/bl616.ini` with an **absolute** `filedir`:

```ini
[cfg]
erase = 1
skip_mode = 0x0, 0x0
boot2_isp_mode = 0

[FW]
filedir = /var/www/own/tang-uknc/bin/bl616.bin
address = 0x000000
```

That is why it does not reuse the SDK's own `mnano/flash_prog_cfg.ini`,
which globs `./build/build_out/misterynano_fw*_$(CHIPNAME).bin` relative
to the current directory and so only works from `mnano/` after a firmware
build.  The generated one flashes the shipped binary with no build tree at
all.

The SDK's own route still works and is the same program underneath:

```sh
make -C mnano flash COMX=/dev/ttyACM0
```

Its `flash:` target is one line, `$(command_flash)`, so it too needs
nothing on `PATH` - but it flashes whatever is in `mnano/build/build_out/`
and fails if that is empty.

## The SD card

The MCU expects a FAT filesystem.  Disk images are `.dsk`, 819200 bytes,
and settings are meant to live in an `.ini` at the card root - see the
`settings_file[]` trap in `CLAUDE.md` before assuming which name.

## Wiring

The two boards are wired to each other; the table is in `README.md` and
repeated in `.claude/docs/fpga.md`.  Since August 2026 it **is** the stock
MiSTeryNano pinout - it was not before, so a board wired from an older
copy of this repository needs rewiring, audio included.  Five signals plus
ground and +5V.
