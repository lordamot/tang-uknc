what is that UCL.SAV file for? I've seen it on some disks - guess it is needed for base RT-11 image

****

UCL stands for User Command Linkage. It is RT-11 V5's hook for adding your own keyboard-monitor commands: when KMON does not recognise a command word and no program of that name exists, it runs SY:UCL.SAV with the command line, and that program decides what to do with it. DEC shipped a sample one, with its MACRO source, that kept a table of user-defined command names and the command strings they expand to, so you could type a short word of your own instead of a long RUN or COPY line. The message you get without it is exactly that hook finding nothing: ?KMON-F-File not found SY:UCL.SAV.

It is not needed for a base image. Nothing in the system calls it except unrecognised command words, and every real command - R, RUN, DIR, COPY, bare program names - works without it. The disks you have seen it on either kept the DEC sample or carried somebody's own set of shortcuts, which is why the file differs from disk to disk. The only effect of leaving it off is the message above for a typo instead of whatever the custom program would have printed.

If you ever want it, the thing to add is a UCL.SAV from a V5.04 distribution together with its definition file, not something to build here, and I would keep BASERT11.DSK as it is.

Built, not run on a board. The firmware is in bin/bl616.bin (437776 bytes); the image code was run on the host and its product booted in the emulator.

What it does. The main OSD form has "Run SAV:" right after HDD 0:, a file selector over *.sav anywhere on the card. Picking a file: the entry's label becomes "making DSK" and the OSD redraws; FDD 0 is ejected; /sd/RT11BASE.DSK (BASERT11.DSK is accepted too) is copied to /sd/RT11SAV.DSK; the program is added under a six-letter RT-11 name; "R NAME" is appended to STARTS.COM after whatever the base had; then the label reads "err: no RT11 base" (or another short reason: bad RT11 base, no SAV file, empty SAV, cannot write, copy failed, disk full, dir full, name taken) or "done: RT11SAV.DSK", and in that case the disk is mounted in FDD 0 and the core is reset so it boots into the program. The label goes back to "Run SAV:" when the OSD closes.

Names: uppercase, RAD50 letters and digits only, the last extension dropped, cut to six; "PROG" if nothing is left; if the base already has a file of that name (dir.sav -> DIR.SAV) it becomes five letters and a digit, so a system program is never overwritten. "Real Time Clock test (Kakave+).SAV" becomes REALTI.SAV.

Blocking: the copy runs inside the OSD task, so no menu event is served until it is over, and the event queue is emptied afterwards - keys pressed during the copy do nothing. The selection lives in a sixth SD slot that the settings file never sees; only FDD 0's mounted image would be saved, and only if Save settings is pressed afterwards.

What the message is. Searching the ROM for it: the text sits between ДВОЙНОЕ ЗАВИСАНИЕ and СТОП, and it reads А.В.П., not А.В.Р. - the PPU's halt text for a bus timeout while receiving the interrupt vector address. So not the floppy: the PPU took an interrupt, ran its vector-fetch cycle, and no device answered in time. Once vs. hang is the CPU and PPU racing, as you said.

Why nobody answered. The PPU's vector strobe is a daisy chain in top.v: core -> xm2-01 (timer 304, keyboard 300) -> vp1_120 (the channels). A chip must pass the strobe on unless it is the one with an enabled request. xm2-01 stopped it whenever its request was merely set, but it acknowledges only when set AND enabled - and a timer or key request is set-but-disabled from the moment its vector is taken until the handler reads 177714 or 177702. A channel interrupt taken in that window - the CPU's byte landing while the PPU is in the first instructions of its timer handler - reached nobody; the fetch timed out; the ROM halted. MKLAD drives the PPU timer and the channel together, so it lives in that window. vp1_120 gated its own chain outputs the same way (its CPU-side one feeds vp65). Both gates are the VIRQ condition now: one line each.

Evidence. sim/tb/tb_virq.v (make virq-test) wires the two chips exactly as top.v does and takes four vectors: the timer, a channel-0 byte with the timer flag still up, a key, a channel-1 byte with the key unread. Against yesterday's RTL the two channel fetches time out - the testbench prints the ROM's message for them - and against the fix they answer 320 and 330. Lint clean; make bitstream 59 s, timing gate passed, resources unchanged (52/28/66); openFPGALoader wrote it and said Done. Written up as progress.md 19, a CLAUDE.md trap, and notes in platform.md and build.md.

If the same message comes back after the power cycle, the next two suspects are named in progress.md 19: a channel request that vanishes between VIRQ and the fetch (one of them follows the CPU's INIT line directly), and the strobe's crossing into vp1_120's 25 MHz domain.
